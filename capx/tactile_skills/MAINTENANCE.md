# 触觉技能库维护规则

这份文档只管一件事：**这个库里能写什么、怎么写、什么时候该重测**。
内容在 `skills/*/*.md`，格式的机械定义在 `library.py`，逐轮的词数记录在 `HISTORY.md`。

## 三条前提

1. **库不是笔记，是 prompt 素材。** 每一条都会进某个任务的 prompt，每条都得值它占的那一行。
2. **摘要就是投递的全部。** compact 渲染只发 `- <名字>: <摘要>`，**正文永远不进 prompt**。
   正文里写的东西，LLM 看不到。
3. **一条规则一个家。** 第二个地方需要它，写指向正主的指针，不写副本。

---

## 零、库里只写"现在该怎么做"

**一条技能说的是今天该做的动作。** 不是它怎么被发现的，也不是哪几轮死过。

- **被推翻的规则直接改写或删掉**，不在库里留墓志铭。理由、测量、反例进 `evidence:` 或正文。
- 写之前先问：**这条今天还成立吗？** API 行为、任务几何、阈值来源任何一处变了，
  它就过期了——那比写得不好更糟，因为它会自信地给出错答案（§四.3）。
- 反例：曾经有一条技能教"伺服落点不准，读数要减掉误差再闭一次"。服务端改成精确落点之后，
  它描述的现象已经不存在了。正确处置是**重写成今天成立的那条**，不是补一句"以前是这样"。

## 一、加一条技能之前，过三道闸

### 闸 1：它是一条技能吗？

| 想写的东西 | 归属 |
|---|---|
| 函数做什么、参数取值范围与取值的依据、返回字段的含义与量纲、服务端行为、硬限制 | **API docstring**（`univtac_api.py`）|
| 任务要什么、成功判据是什么 | **任务 PROMPT** |
| 拿读数**怎么下判断**、先做什么后做什么、错了怎么退 | **技能库**（这里）|
| 这样试过，不行 | **不进库** |

**最容易判错的是"读数的含义" vs "读数的用法"。** 判据两问：
**"这在任务不存在时还成立吗"**——成立 ⇒ API 的性质；**"这是不是给我一个动作指令"**——是 ⇒ 技能。
一个数字可以合法地出现在两边，只要说的是不同的话。

**反方向也会错，而且更隐蔽：摘要整句只是字段定义，没有指令。**
自查一句话：**这条摘要，去掉它 LLM 会做错什么？** 答不上来就说明它只在复述 docstring。

**"别这么做"没有投递目标**，因此不进库——测试 `test_every_skill_reaches_some_task` 钉的就是这个。

### 闸 2：库里已经有它的家了吗？

1. 拿关键名词和**数字**在 `skills/` 里搜一遍（数字最不会撒谎）；
2. 读候选技能的 `## How` 和 `## Traps`——规则常常已经躺在别人的陷阱条目里；
3. 看候选技能的 `copies:`。

命中就**改那一条**，不要新建第二条。

### 闸 3：它投递给谁？

没有落点的技能就是死文件。三个键选一个：

- `task_types: [<类型>]` —— **默认**。类型在 `taxonomy.yaml`。
- `task_types: []` + `tasks: [<任务名>]` —— 两种情况：
  带**按物体标定的数字**（同类型别的任务不能拿到它），或讲的是**某一任务自己的流程**
  （判据：把任务名换成同类型另一个，这句话还成立吗？不成立 ⇒ 走任务名）。
- `task_types: [<其余类型>]` + `tasks: [<其余任务名>]` —— 把一个任务从类型规则里摘掉。
  只在"这条规则对那个任务是**假话**"时用；单纯"用不上"不算。
  `not_tasks` 是同一件事的写法（见 `_base_task` 的用法）。

任务名必须与 `env_configs/univtac/*/low_level_*.yaml` 的 `task_name` 一致，写错加载期就报错。

## 二、怎么写

### 2.1 骨架

```
skills/<family>/<name>.md，family ∈ sense/act/place/protocol，文件名 = name
```

```markdown
---
id: S1                    # 稳定短号，不复用
name: depth-grip-scale    # 必须等于文件名
family: sense
summary: 一行，就是投递出去的那一行
task_types: [classify, insert, manipulate, screw]
channels: [depth]         # 可选
objects: any              # 可选：这些数字在什么物体上量的
evidence: 为什么信它，带 n 和实测区间   # 必填
copies: []                # 可选
---

## How
怎么做。

## Traps
最容易踩反的地方。
```

未知字段会报错，不是忽略。

### 2.2 摘要——唯一有硬约束的地方

**一行一件事，先给动作，再给一个数字；条件和例外进正文。**

- 不写"因为……所以……"，理由、阈值来源、失效条件放 `evidence:` 或正文。
- 命令式、英文，和库里其他行同一个语气。
- 写之前先看有没有一句话是同一件事的第二次表述——有就删掉。
- 测试卡每类合计的词数上限；常量在测试里，别凭记忆。

⚠ **写完必须验，不能只看文件里有。** 用
`TactileSkillLibrary.default_library().render_for_task("<任务名>")` 打出来，
确认那一行真的在投递块里。**这是本库最常踩的坑：把规则补进 `## How`，补了等于没补。**

### 2.3 正文

`## How` 讲怎么做，`## Traps` 收最容易踩反的地方。正文字数不影响 prompt 预算，宁可写全。
引用另一条技能用 `[[技能名]]`（名字写错测试会报）。

### 2.4 数字的纪律

每个阈值都要能回答两个问题：**在什么物体上量的**、**n 是多少**，写在 `evidence:` 里。

按物体标定的数字**互不通用**：把方块上的分界值拿去罐上不会报错，会返回一个大小合理的错答案。

## 三、合掉或删掉一条技能

合并比新增危险，因为它会**静默改变别的任务的投递**。

1. **先查路由覆盖面**：把两条各自覆盖的任务列出来，确认幸存那条覆盖得住被删那条。
2. **改指针**：别的技能里 `[[被删的名字]]` 要一起改，测试会报悬空。

## 四、检查

### 4.1 机器检查（动库就跑）

```bash
./.venv/bin/python -m pytest tests/integrations/test_tactile_skills.py -q
```

它抓格式和路由：任务名与配置不符、未知类型/任务、文件名与 slug 不符、重名、未知字段、
`[[指针]]` 悬空、有条目够不到任何任务、字数超预算、读不到凝胶的任务不发技能块、
每个配置都能解出自己的任务名。

**桩必须从真配置来**：路由的测试曾经用自己捏的 `SimpleNamespace` 桩，于是一个
"名字永远解析成空、技能块一次都没进过 trial"的 bug 让 39 条测试全绿。

**它抓格式，抓不到内容。** 下面三节才是这份文档的重点。

### 4.2 人看的检查

- **重复是不是又长出来了。** 同一个规则的第二次表述是常态，合并过一次不等于不会再长。
- **`copies:` 里只该有文档**（`docs/` 下的参考文档），出现 prompt 或 docstring 就是新长出来的假线索。
- **投递量是不是在悄悄长。** 测试只卡上限，每次加一点点不会被拦下；持续往上走是"该合并了"的信号。

### 4.3 触发式检查（发生了就必须做）

**上游同步、任务几何或 API 行为变了之后，库里相关的数字不是过期，是错的。**

1. 列出这次改了几何/材质/行程/接口的物体和字段；
2. 搜出有这些数字的技能（`objects:` 和摘要里的阈值）；
3. 重跑测量，更新 `evidence:` 的 n 和实测区间；
4. 更新摘要里的阈值，**再用 `render_for_task` 复核那一行真的变了**。

任务改名或新增任务之后：改 `taxonomy.yaml`，跑 §4.1。

### 4.4 没有内容回归网

**加一条技能会改十几个任务的 prompt，而没有任何自动检查能告诉你分数变好还是变坏。**

所以：**库的每次内容改动，在跑过 eval 之前都算未验证。**
"测试全绿"只说明格式和路由没坏。
